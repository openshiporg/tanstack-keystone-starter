# Keystone–Prisma Layering Dissertation: NKS vs TanStack Target

## 1) Executive Summary
This audit confirms your core complaint: **Next Keystone Starter (NKS) delegates Prisma mediation to Keystone runtime internals**, while `tanstack-keystone-starter` currently implements a **clean-room CMS runtime that directly maps CMS semantics to Prisma adapter calls**.

That means the target is not architecturally equivalent at layering boundaries, even where behavior appears similar.

- In NKS, Prisma is a persistence substrate hidden behind Keystone list/field/access/hooks/session/auth pipelines.
- In TanStack target, Prisma is an explicit adapter implementation (`src/features/cms/adapters/prisma.ts`) and a generated-prisma-schema pipeline (`src/features/cms/prisma-schema.ts`, `scripts/cms-generate.ts`) controlled by local runtime code.

This is not inherently wrong for clean-room parity, but it creates mismatch in:
- migration/seed ownership and expectations,
- auth/reset/storage/document semantics,
- schema/mutation contracts,
- and UX/runtime behavior coupling.

## 3) How NKS Actually Layers Keystone Over Prisma
## 3.1 Keystone is the runtime authority
NKS entrypoint:
- `keystone.ts` exports `features/keystone/index.ts` config.

In `features/keystone/index.ts`:
- `createAuth` from `@keystone-6/auth`
- `config` from `@keystone-6/core`
- `statelessSessions` from `@keystone-6/core/session`
- models defined via Keystone field/list DSL
- `graphql.extendGraphqlSchema` extension for `redirectToInit`

This means list DSL, access control, hooks, auth flows, GraphQL schema, Prisma schema/migrations expectations are all coordinated by Keystone machinery.

## 3.2 Prisma is wired through Keystone context internals
`features/keystone/context.ts`:
- uses `getContext(config, PrismaModule)` from `@keystone-6/core/context`
- passes `@prisma/client` module into Keystone context factory
- hot-reload safe singleton pattern.

So Keystone owns request context and db/query APIs; Prisma Client is consumed by Keystone internals, not by custom adapter translation code.

## 3.3 Build/migrate lifecycle is Keystone-first
NKS scripts (`package.json`):
- `dev`: `keystone build --no-ui && npm run migrate && next dev`
- `build`: `keystone build --no-ui && npm run migrate && next build`
- `migrate:gen`: `keystone build --no-ui ... && keystone prisma migrate dev`
- `migrate`: `prisma migrate deploy`

Interpretation:
- Keystone build generates/validates Keystone artifacts and Prisma contract first.
- Migrations are expected to align with Keystone-generated schema pipeline.

## 3.4 Seed expectations in NKS
There is **no app-local `prisma/seed.ts` in NKS root** in audited files. Initialization path is primarily:
- auth `initFirstItem` (`createInitialUser`) + runtime-created role default,
- optional external migration/seed ops outside this repo surface.

So user expectation “Keystone should own persistence behavior” is consistent with NKS architecture.

## 4) How TanStack Currently Layers Runtime Over Prisma
## 4.1 Local runtime is authority
`src/features/cms/runtime.ts` builds:
- custom GraphQL schema and resolvers,
- custom context APIs (`context.db`, `context.query`, `context.graphql`, transactions),
- custom auth schema overlay via `addAuthGraphQLSchema`.

## 4.2 Prisma adapter is explicit and custom
`src/features/cms/adapters/prisma.ts` does manual mapping:
- CMS filters/order/relations -> Prisma where/order/include shapes,
- relation connect/disconnect/set/create handling,
- access checks and hooks around Prisma calls,
- context transaction wrapping.

This is a clean-room equivalent effort, but not Keystone runtime.

## 4.3 Prisma schema is generated by local CMS printer
`src/features/cms/prisma-schema.ts` and `scripts/cms-generate.ts` generate `.cms/schema.prisma` + compare against `prisma/schema.prisma`.

So schema authority is your custom generator, not Keystone CLI.

## 4.4 Seed is app-local direct Prisma seed
`prisma/seed.ts` manually creates roles/users/todos/images using Prisma client. This diverges from NKS’s practical init-first flow and Keystone-owned pipeline semantics.

## 5) Root Layering Mismatch (Your Exact Complaint)
You’re observing a real mismatch in responsibility boundaries:

1. **NKS:** Keystone runtime mediates Prisma.
2. **TanStack target:** custom runtime mediates Prisma directly.

Consequences:
- behaviors that “feel Keystone” can still differ subtly,
- seed/init/reset/storage semantics diverge,
- dashboard assumptions from NKS are often invalid against current target contract,
- debugging burden shifts from Keystone internals to custom adapter/runtime logic.

## 6) Parity Gaps by Domain
## 6.1 Auth/init/reset
- `createInitialUser` exists in target and matches naming shape.
- password reset link flow in target is still incomplete vs NKS (`passwordResetLink.sendToken` path in NKS).
- target temporarily dropped nested role create in init (`cms.config.ts` currently `itemData: {}`), which is intentionally less equivalent than NKS.

## 6.2 Storage/image/document
NKS uses Keystone `storage.my_images` (S3 image field) + document field package integration.
Target supports image/document/json shapes in schema layer but lacks full Keystone storage lifecycle parity and upload pipeline parity.

## 6.3 Access/hooks/context semantics
Target has significant parity work, but this is still local implementation parity, not Keystone internals. Edge cases remain likely.

## 6.4 Migration/prisma ownership semantics
NKS: `keystone build` + Keystone-prisma mediation.
Target: custom `cms:generate` + local prisma schema printer + custom delegate checks.

This is the deepest architectural fork.

## 6.5 Dashboard contracts
NKS dashboard depends on Keystone-admin style field controllers/views and richer action stack.
Target dashboard currently only partial parity; many flows remain scaffold-level.

## 7) Reconciliation Strategy (Two Viable Paths)
## Path A (recommended given current constraints): Keep clean-room runtime, enforce stronger behavior parity
Pros:
- aligns with “no direct Keystone runtime import” constraint.
- preserves TanStack-native control.

Cons:
- highest ongoing implementation burden.
- parity drift risk remains high.

## Path B (not current policy): import Keystone runtime internals directly
Pros:
- fastest parity on backend semantics.
Cons:
- violates current project direction/constraints.

Given constraints, **Path A** is mandatory.
