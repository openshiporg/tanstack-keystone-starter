# CMS Runtime / Keystone Core Parity Audit

## 1. Verdict

Not full parity

The local CMS runtime is not a thin import of Keystone and it is not full Keystone runtime parity. It has meaningful Keystone-shaped behavior: list initialization exists, GraphQL CRUD names are largely Keystone-like, public/internal schemas exist, many mutations return ordered settled arrays, admin-meta hides query-omitted relationship targets, auth exposes the expected core mutation/query names, and `context.db` / `context.query` now execute through GraphQL schema fields rather than being only a loose adapter facade. Those are real slices, not just scaffolding.

The blockers are still contract-level, but the storage lifecycle depth slice is verified. Helper-level lifecycle coverage now proves configured local image unchanged/replace/delete behavior, configured local file replace/delete behavior, and remote-style file lifecycle helper behavior through the real `cleanupReplacedFiles(...)` / `cleanupDeletedItemFiles(...)` paths, including remote DELETE requests for configured remote storage keys. The remaining storage/upload blocker is now primarily the explicit architectural non-parity that local GraphQL upload handling buffers streams fully into memory instead of streaming directly to a storage strategy, plus exact official storage config API differences.
